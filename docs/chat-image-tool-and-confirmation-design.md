# 聊天模型调用图片模型与 ask_user 确认流程设计草案

状态：讨论稿，尚未实施本方案。

整理日期：2026-09-13。

用途：合并两次讨论，作为后续需求确认、技术设计、实现和回归测试的参考。

本文区分“现有能力”“推荐方案”和“待决定事项”。工具名、任务字段及界面文案均为建议，不代表已注册的接口或已发布功能。2026-09-15 随开发文档公开供讨论，公开本文不表示已实施方案或已发布安装包。

## 1. 需求与结论

目标体验：用户发消息，聊天模型先回复一段文字，再调用用户配置的图片模型，图片生成后回到聊天中，聊天模型继续第二段回复。

在此基础上，复用 `ask_user` 询问本次是否生成图片，并允许用户选择原始提示词、模型优化后的提示词，或者手动修改后再生成。生成后可选地询问后续操作。

结论：可行，且适合作为现有聊天生图功能的可选升级。应用负责请求转发、等待、保存、授权和模型续答，并非两个模型直接通信。聊天模型与图片模型可以来自不同供应商。

主要价值在图文创作、海报与视觉方案讨论、角色扮演中的场景图和立绘。普通问答不必开启；不应因用户配置了图片模型，就默认允许聊天模型随时产生生图费用。

主要成本不是重新接入图片 API，而是任务状态、消息一致性、参数快照、费用控制及多协议回传的可靠性。

## 2. 已有实现与缺失部分

以下为整理时检查到的代码基础，不代表所有供应商和设备组合已经验证。

| 已有基础 | 可以复用的部分 | 仍需补齐 |
| --- | --- | --- |
| `ChatImageGenerationService` | 调用图片模型、按能力约束参数、将生成图片保存为聊天附件 | 与已确认任务绑定、可观察进度、失败恢复及结果复用 |
| `ImageGenerationRequestState` 与 `ChatImageGenerationSettings` | 图片页和聊天参数面板共享状态及参数转换 | 冻结用户确认时的模型、供应商与最终参数 |
| `GenerationHandler` | 模型输出、工具执行、工具结果回传和继续输出的循环 | 注册生图工具，连接确认状态，避免重复执行 |
| 消息与工具结果 | `UIMessagePart.Image`、工具结果图片展示，以及部分协议的图片回传路径 | 三种协议和无视觉模型的行为核对；生图结果与续答顺序 |
| `ask_user` | 单选、文本输入、预填内容、条件联动、取消和过期处理 | 生图专用确认与执行授权的可信绑定 |
| 聊天生图界面 | 图片模型显示、参数面板、等待占位和预览基础 | 将等待区域准确绑定到本次工具任务 |

现有 `ChatVM.generateChatImage()` 是手动发送路径，会追加用户提示词及独立助手图片消息。不能直接将这个 UI 方法注册为工具，否则容易重复写入用户消息、打乱回答顺序，或与正在生成的聊天消息竞争。

推荐复用其底层服务，而不是复用这个会直接改写消息列表的入口。工具生图由生成链路统一提交结果，不能同时由工具和 ChatVM 各写一遍图片。

## 3. 推荐端到端流程

1. 用户明确提出生图需求，应用检查是否已配置可用图片模型、聊天模型是否支持工具，以及本助手／对话是否允许调用生图。
2. 聊天模型可以先说明设计意图，再提出候选生图提示词。
3. 应用创建待生成任务，保留用户原文、模型候选提示词、当前图片模型及参数快照。
4. 使用 `ask_user` 的交互能力呈现确认表单，等待用户选择或修改。
5. 用户明确提交后，应用校验并锁定最终请求，将授权绑定到该任务；未确认不得调用图片供应商。
6. 图片生成期间显示任务内等待区域；允许用户取消，不阻塞用户切换页面或对话。
7. 图片成功落盘，持久化任务结果，并在聊天中显示图片及图片模型名称。
8. 将工具结果回传给聊天模型，继续第二段回复；第二段重试复用已保存图片。
9. 可选展示生图后的反馈表单。用户不操作也能阅读已完成的回复。

界面可以表现为同一次回答中的“第一段文字 → 生图区域 → 第二段文字”。底层通常包含多次 API 请求，不要求是一条不断开的网络流，也不强制将所有内容存成同一条数据库记录；关键是关联清晰、顺序稳定、可恢复。

### 第一段回复的限制

支持工具的聊天模型不一定在调用前先输出文字。提示词和工具说明可以引导，但不能保证所有模型严格遵守。

推荐第一阶段允许“模型直接请求生图、应用显示确认卡”的情况，不为固定格式额外增加一次模型请求。如果产品要求每次都必须先有文字，应由应用额外编排，并接受时延和费用增加；应用状态提示不能冒充模型原话。

## 4. 生图前的 ask_user 确认设计

### 4.1 一次紧凑确认，避免连续问卷

建议表单示意如下。这是交互示意，不是现有工具的可直接调用 JSON。

> 本次生成 1 张图片，使用模型：XXX
>
> 主要参数：比例／尺寸、质量等当前实际生效选项
>
> 提示词方案：使用原始提示词／使用模型优化版／手动修改／本次不生成
>
> 查看原始版 ｜ 查看优化版
>
> 选择手动修改后显示文本框
>
> 确认并生成 ｜ 取消

- 使用单选表达提示词方案，应用保留稳定的选项值，不以模型复述的标签作为授权依据。
- 原始版和优化版都可展开完整预览，长文本不放在选项标签里。必要时提供全屏查看／编辑，适配手机。
- “手动修改”通过 `visible_if` 联动显示文本字段，可预填一个候选版本。预填哪个版本见待决定事项。
- 隐藏字段不应参与提交；选择原始版时，不得读取隐藏的手工文本覆盖原文。
- 选中选项、预填默认值或打开表单都不是同意。只有明确提交生成才授权。
- 如选择“本次不生成”，提交动作应为“继续对话”，不能继续显示容易误解的“确认并生成”。
- 无可靠价格来源时只提示“可能产生费用”，不要编造精确预估。

### 4.2 原文、优化版和最终版必须分开

“原始提示词”应由应用从真实用户输入中保存，不由聊天模型重新复述。用户消息同时包含聊天指令和生图描述时，如何界定原文需要明确：默认保留完整来源，并向用户展示实际准备发送的文本，不能静默抽取或改写后仍称为原文。

建议保留三份逻辑上独立的文本：

- 原始版：用户提供的、可追溯到来源消息的文本快照。
- 优化版：聊天模型拟定的候选版本，未经用户接受不得当作最终版本。
- 最终版：用户明确选择或手工编辑并确认的版本。

最终提交后，聊天模型不得再次“润色”并替换最终版。若确需更改提示词，必须形成新修订并重新确认。

### 4.3 倒计时与等待

普通生图确认不建议启用短倒计时，用户需要时间检查内容。现有 `ask_user` 的确认类型可以按需启用倒计时，但超时只能意味着不执行，不能自动同意。

表单取消、拒绝、过期、参数无效都不能授予生图权限。现有通用 `ask_user` 请求仍有整体有效期，不应描述为无限等待；超期后可重新发起确认。

## 5. ask_user 与执行授权之间的边界

仅向模型写入“请先调用 ask_user，再调用生图工具”并不可靠。模型可能跳过询问、并行发起两个工具，或在收到回答后修改参数。

现有 `ask_user` 契约也明确指出：收集回答不能替代执行工具自身的审批。需要由应用建立正式的授权衔接，而不是凭模型说“用户已经同意”就执行。

推荐待生成任务至少记录下列信息，实际存储结构待实现时确认：

| 信息 | 用途 |
| --- | --- |
| 任务 ID、对话 ID、源消息／回答分支 ID | 回写到最初对话，避免切换页面后串写 |
| 原始版、优化版、最终版及修订号 | 可预览、可追溯，不混淆提示词来源 |
| 图片模型、供应商路由与最终参数快照 | 审批展示和实际请求一致 |
| 关联 ask_user 请求、用户提交记录与有效期 | 验证该任务确实获得本次确认 |
| 最终请求摘要／哈希 | 发现提示词、数量、模型等在确认后发生变化 |
| 执行状态、供应商任务 ID（如有）、结果附件 | 防重入、恢复和复用已生成图片 |

哈希只能检测内容变化，不能证明用户同意；授权记录必须由应用的可信交互和校验流程产生，不能相信模型传入的 `approved=true` 或伪造任务字段。

执行工具（暂称 `generate_image`）应读取已授权任务，不能仅根据模型重新提交的一份提示词开始消费。模型、数量、尺寸、质量、参考图或提示词发生有效变化，都应使旧授权失效。约束校验应尽量在确认前完成；执行时若必须改变参数，应回到确认，不静默换模型。

可以让一次用户确认同时完成意图选择与该任务的执行审批，避免重复弹窗；前提是实现上述校验桥接。桥接尚未完成时，不能直接取消原有执行审批。

## 6. 参数、图片回传与上下文

### 参数复用

图片模型、数量和质量等默认继承用户现有配置，复用共享状态与 `ImageGenerationConstraints`。聊天模型主要提供提示词，只允许调整明确开放、且当前模型支持的参数。

在现有能力查询接口中可增加生图可用状态、允许调整的参数和限制。未配置、供应商关闭或不支持生成时，应隐藏／禁用入口及相关工具，不能假装生成成功。

### 图片展示不等于模型看过图片

- 支持图片输入的聊天模型：在协议允许的形式下回传实际图片，随后可以基于图片续答。需核对 OpenAI、Google、Anthropic 及兼容网关的工具结果媒体支持。
- 不支持图片输入的聊天模型：返回状态、提示词摘要和图片数量等文本信息。它可以继续聊天，但不能声称已经检查图片细节。
- 回传图片可能增加输入 Token、带宽和时延，应避免重复编码、重复注入和回传过大的图片。
- 图片保存在消息附件中，是后续上下文处理的来源，不代表每次都必须将所有历史生成图再次发送。

### 世界书与角色扮演

聊天模型可依据本轮实际采用的设定，整理人物外观、服饰、场景等必要视觉信息；不要默认把整本世界书、系统提示词或全部聊天历史转发给图片供应商。

优化版应让用户能检查模型添加的细节是否偏离设定。角色连续性需要稳定描述和参考图等机制，不能承诺只靠固定种子保持人物一致。图片编辑或参考图能力必须按模型和服务链实际支持情况开放。

## 7. 生图后的可选询问

建议先展示图片并完成第二段回复，再可选展示轻量反馈卡：

- 继续对话。
- 调整提示词，再生成一张。
- 使用相同提示词生成另一张。
- 基于这张图修改：仅在完整编辑调用链可用时显示。

图片应在询问前保存，不等待用户选择“保留”。不满意不等于删除旧图；删除需要独立、明确的用户操作。

“调整后生成”或“再生成一张”是可能产生新费用的新任务，应重新确认。“重试第二段文字”则复用旧图，不能触发生图。

## 8. 故障、恢复与费用控制

建议将任务状态与展示状态分开，至少区分待确认、已确认、生成中、图片已保存、续答中、已完成，以及取消、过期、失败和结果未知。

| 情况 | 推荐处理 |
| --- | --- |
| 用户拒绝／确认过期 | 不请求图片模型；聊天可继续 |
| 模型同时发出询问和生图调用 | 执行层仍校验任务授权；未确认的生图调用不得执行 |
| 网络失败但供应商可能已接收并计费 | 标记结果未知；有查询接口时查询任务，不能盲目自动重复 POST |
| 图片成功、第二段回复失败 | 保留图片，单独重试续答 |
| 图片返回但本地保存失败 | 不报告整体成功；优先尝试保存／取回已有结果，不自动重新生图 |
| 切换对话／助手 | 回写最初绑定的对话及回答，不使用变化后的当前页面 ID |
| 应用进入后台或进程终止 | 已持久化状态用于恢复；常驻通知或协程本身不等于任务一定不会中断 |
| 原对话／目标回答已删除 | 不悄悄重建或写入其他对话；明确处理孤立结果 |
| 用户重新生成聊天回答 | 明确区分复用旧图和新生图，不继承到不匹配的任务授权 |

应用可以避免重复执行已知完成的任务，但不能仅靠客户端 ID 保证供应商“恰好执行一次”。幂等键、任务查询和取消能力必须按供应商核实。取消本地等待也不保证上游停止生成或退款。

## 9. 推荐实施顺序

### 第一阶段：可控的基本闭环

1. 定义生图任务、快照、授权校验和去重规则，明确由哪一层负责消息回写。
2. 注册工具及能力说明，底层复用 `ChatImageGenerationService` 和共享参数转换。
3. 接入 ask_user 式确认，支持原始版、优化版、手工编辑及取消；保留既有工具审批边界。
4. 接入任务级等待区域、图片模型标记、落盘与结果回传。
5. 接通聊天模型续答，确保图片成功后续答重试不会重复生图。
6. 完成取消、失败、切换对话和重启恢复的回归测试后，再扩大能力范围。

第一阶段建议限制：用户明确要求生图才提供方案；每次确认默认一张图、一次生成任务；不允许模型自行多轮生成或反复修图。原有手动生图保留。

### 后续阶段

- 可选的生图后反馈表单和修改提示词再生成。
- 参考图／图片编辑、角色连续性支持。
- 更完整的供应商任务查询、幂等与恢复能力。
- 按用户明确设置开放自动确认、模型主动建议插图等模式，并配置费用与次数上限。

后续阶段均需单独确认，不因本讨论稿存在就视为已经决定或授权上线。

## 10. 待继续讨论的决策

1. 开关以助手为主、对话覆盖，还是只在当前对话启用？配置图片模型后是否提示用户选择，但不自动开启？
2. 默认选原始版还是优化版？手动编辑默认基于哪个版本？是否提供差异对比？
3. 用户消息混有聊天说明时，“原始提示词”是整条消息还是用户明确选中的片段？
4. 是否必须始终有第一段模型文字，还是接受模型直接发起确认卡？
5. 多模态聊天模型是否默认收到实际生成图？用户是否可关闭，或选择较低回传分辨率？
6. 生图后反馈默认关闭、按需出现，还是由助手设置决定？
7. 后台生成期间允许继续发送新消息吗？若允许，任务与后续聊天如何排序？
8. 同一用户请求生成多张图、多个生图工具并行时，采用何种确认与费用上限？
9. 哪些供应商提供可靠的任务查询／幂等能力？结果未知时的人工重试提示应如何呈现？
10. 是否将确认预览做成通用 ask_user 扩展，还是复用其组件、为生图保留专用任务面板？

## 11. 验收与回归清单

- 正常闭环：文字、确认、等待、图片、续答的顺序正确，图片不重复写入。
- 提示词选择：原始、优化、手工版实际请求均与用户所见一致；原文不由模型伪造。
- 授权：默认值、取消、过期、错误表单、跨对话任务 ID、并行调用和确认后改参都不能绕过校验。
- 参数：共享参数约束生效；模型切换或参数不兼容时不会静默变更已确认请求。
- 费用与恢复：重复提交、网络重试、续答重试、应用重启不重复执行已知完成的生成任务。
- 协议：分别验证 OpenAI、Google、Anthropic 工具往返，以及纯文本模型和第三方网关的降级行为。
- 移动体验：长提示词可完整查看／编辑；键盘不挡确认按钮；等待卡不挤占输入栏；图片适配宽图与超长图。
- 世界书：只发送必要的视觉设定，不泄漏整本世界书或其他未授权上下文。
- 诊断：记录任务阶段、选定模型、参数和错误，屏蔽凭据；完整日志及导出遵循既有隐私设置。

验证应区分单元测试、真机交互测试与真实供应商调用。源码检查或模拟测试不能证明实际供应商不会重复收费。
