## 原审查建议（落地状态见上）

1. **聊天内容加载与导航分离。** ChatPage 的 AnimatedContent 以会话 ID 加加载阶段为 key；加载状态变化会替换内容树。优先改为稳定列表与覆盖式小型加载提示，已有内容保留；只在会话 ID 真正变化时淡入淡出。不要把恢复滚动绑定动画时长。
2. **统一加载状态。** WebView 同时有原生进度、页面绘制状态和 JS 看门狗；进度 100% 并不等于图形绘制完成。建议区分资源加载、布局绘制、失败，并对短加载延迟显示，防止指示条闪现。
3. **统一减少动态效果策略。** ReasoningFlow 已检查生命周期、屏幕可见性、导出和系统动效开关；Shimmer 只检查 isLoading。建议复用同一门控，在后台、屏幕外、导出及低动态模式下提供静态占位，避免多条工具同时运行无限动画。
4. **限制布局动画。** ChatMessage、ChainOfThought、翻译等处仍有 animateContentSize；长文本或动态工具内容频繁变高容易影响列表定位。仅对用户主动展开/收起执行短动画，流式更新保持稳定布局。
5. **合并转场规范。** RouteActivity 的导航缩放和 ChatPage/ChatList 的内部淡入、缩放叠加；建议导航只负责页面转换，内部模式切换尽量只淡入淡出，统一时长和减少动态效果策略。
6. **渐变与玻璃预算联动。** GradientBackground 已在 RESUMED 时才推进动画，现有节流应保留；后续与拖动、流式输出和 WebView 数量共享性能预算，避免多个独立动效各自达到上限。
7. **真实设备测量。** 针对长消息结束、全屏往返、后台恢复、工具列表、生图加载各采集帧耗时、峰值内存和原生 View 生命周期，再判断动画收益。JVM/浏览器测试不能验证 Android GPU 与原生双指触摸。
